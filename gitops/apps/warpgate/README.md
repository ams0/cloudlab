# Warpgate

[warp-tech/warpgate](https://github.com/warp-tech/warpgate) — a smart bastion
for SSH, HTTP, MySQL and Postgres, with a browser-based admin UI and session
recording.

UI: `warpgate.vps.kubespaces.cloud`

## Resources

- `namespace.yaml`
- `warpgate-gitrepository.yaml` — Flux GitRepository pinned to tag `v0.29.0`
- `warpgate-db-helmrelease.yaml` — CNPG PostgreSQL 18
- `warpgate-pvc.yaml` — 2Gi local-path for `/data`
- `warpgate-helmrelease.yaml` — the chart from `./helm/warpgate` in that repo

The OIDC client is `gitops/keycloak-resources/warpgate-client.yaml`.

## HTTP only, deliberately

Warpgate is a bastion: it also listens for **SSH, MySQL and Postgres**, and all
three are raw TCP. This cluster's only ingress path is HTTP —
Traefik `:443` → Istio gateway NodePort → HTTPRoute — so those protocols are set
to `0` rather than exposed on a Service nothing outside can reach. The admin UI
and HTTP target proxying work today.

**To add SSH later** you need all four of:

1. a TCP listener on the shared Gateway (`gitops/gateways/gateway.yaml`)
2. a `TCPRoute` — the experimental Gateway API CRDs are already installed, so
   `tcproutes.gateway.networking.k8s.io` exists
3. a host firewall rule (`roles/common` opens 22, 80, 443, 6443, 8000, 9000 —
   8000 and 9000 are currently unused)
4. a matching **OCI security-list** rule in `terraform/` — iptables alone is only
   half the path

Port 22 belongs to the host's sshd, so Warpgate's SSH needs a different port.

## Why a GitRepository source

Warpgate publishes no chart to any registry; the official one lives in-repo at
`helm/warpgate`. The repo is ~9MB, so pulling it through Flux is cheap — the
same pattern Garage uses. (Contrast OpenCloud, whose 1.8GB monorepo forced
vendoring the chart into `charts/` instead.)

Pinned to the release **tag**, not a branch: the chart's own `version` is stuck
at `0.1.0` and never bumped, so the tag is the only meaningful version signal.

## Config and secrets

SSO providers have no values-level knob, so the chart's generated config is
replaced wholesale via `overrides_config`, based on its own `warpgate.config`
helper with `sso_providers` and `external_host` added.

Nothing sensitive is in Git. `config_env_var_replace` lists the variables
Warpgate substitutes from the pod environment at startup:

| Variable | Source | Vault key |
|---|---|---|
| `WARPGATE_DB_PASSWORD` | CNPG `-app` secret | *(generated by CNPG)* |
| `WARPGATE_SSO_CLIENT_SECRET` | `warpgate-sso` | `vault_warpgate_sso_client_secret` |
| `WARPGATE_ENCRYPTION_KEY` | `warpgate-secret` | `vault_warpgate_encryption_key` |
| `WARPGATE_ADMIN_PASSWORD` | `warpgate-secret` (setup Job only) | `vault_warpgate_admin_password` |

`WARPGATE_ENCRYPTION_KEY` encrypts stored target credentials at rest — losing it
makes every saved target credential unreadable.

## Routing

The chart emits a Gateway API HTTPRoute itself, so unlike other apps here there
is no separate `warpgate-httproute.yaml` — one fewer place for the backend
service name to drift out of sync.

## First login

The setup Job seeds an `admin` account from `WARPGATE_ADMIN_PASSWORD`. Keycloak
SSO appears alongside it as "Kubespaces". Keep the local admin: it is the
break-glass path if OIDC or the realm breaks.
